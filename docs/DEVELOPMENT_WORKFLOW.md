# 開発ワークフロー

このドキュメントは `bbs3d_ros2` の開発手順の唯一の真実 (source of truth) です。すべての変更(コード・ドキュメントを問わず)はこのワークフローに従って main に取り込みます。

## 原則
1. **main への直接 push は禁止**。すべての変更は Pull Request 経由でレビューを通してから main にマージする。
2. **1 Step = 1 ブランチ = 1 PR** を原則とする。Step は [`IMPLEMENTATION_PLAN.md`](IMPLEMENTATION_PLAN.md) の Step 0〜10 を指す。
3. **コード変更前に必ず計画フェーズを通す**(下記「計画フェーズ」)。plan mode で実装計画を提示し、ユーザの明示的承認を得てから実装に入る。
4. **ROS 2 ノードの機能追加は TDD で進める**(下記「TDD フロー」)。テスト可能な機能はテストファーストで実装する。
5. **`3d_bbs/` 以下は変更しない**。上流 submodule への変更が必要な場合は本リポジトリではなく上流 ([KOKIAOKI/3d_bbs](https://github.com/KOKIAOKI/3d_bbs)) に issue / PR を出す。

## 計画フェーズ(実装前に必須)

コード・CMake・テストの変更に着手する前に、必ず **plan mode** で以下を提示し、ユーザの明示的承認を得る。**承認なしに実装を開始しない**。

提示すべき内容:
- **何を作るか**: 対象ファイル、追加・変更する関数 / API / トピック / 設定項目
- **どう作るか**: アプローチ、依存関係、設計上のトレードオフ、上流互換性への影響
- **TDD 適用時は RED テスト設計**: テスト粒度、テストフレームワーク (gtest / `launch_testing` 等)、テストデータの所在、想定される失敗ログ
- **代替案がある場合は複数案を提示**: 各案のメリット / デメリット、推奨案

これは TDD フロー(下記)の前段に当たる。複数の実装パスがありうる場合や、ユーザの環境・好みに依存する判断(テストデータの場所、依存ライブラリの選択など)が含まれる場合は特に重要。

ここでの「plan mode」とは: 計画を提示し、ユーザが明示的に承認するまで実装に入らないこと。Claude Code の plan mode 機能(`EnterPlanMode`)を使うことを推奨する。会話形式で計画を提示してユーザが「OK」「承認」等と返すのも plan mode 相当として扱う。

**ドキュメントのみの変更**(`*.md` のみの編集)は計画フェーズを省略してよい。CMake・コード・テストが 1 行でも含まれる変更は対象。

## TDD フロー(ROS 2 ノード機能の追加・修正)

ROS 2 ノードの機能(トピック I/O、Service ハンドラ、コールバックロジック等)を追加・変更する場合は、以下のサイクルを **PR 作成前に** 完了させること。ドキュメントのみ・CMake のみ・rviz / launch 設定のみの変更は対象外。

> **前提**: 上記「計画フェーズ」を通過し、ユーザの実装計画承認が取れている状態から開始する。フロー全体は **plan → ユーザ承認 → RED → ユーザ承認 → GREEN → ユーザ承認 → PR**。

### 1. RED — 失敗するテストを書く
- 期待する仕様を検証するテストをまず書く。
- **テストはビルドが通り、実行時に意図通り失敗する状態にする**。
- **ビルドエラーは RED として認められない**。テストロジックが動いた結果として失敗していることをログで示す必要がある。
- 例(gtest): `colcon test --packages-select bbs3d_ros2` がテスト実行までは到達し、該当ケースだけが FAIL している状態。

### 2. RED の承認をユーザから得る
- ユーザに以下を提示する:
  - **テスト観点**: 何を検証しているか(例:「`/click_loc` に true が来たら `/global_pose` が 1 つ publish される」)。
  - **失敗ログ**: ビルドが通った上で意図通り失敗していることの証跡。
  - **テストファイルのパス**と該当ケース名。
- 承認が取れるまで GREEN 実装には進まない。

### 3. GREEN — テストを通す最小実装
- テストが通る最小限のプロダクションコードを書く。
- 上流挙動を維持する方針(`CLAUDE.md` の「規約」)を守る。
- リファクタは必要最小限に留め、別 PR にしてもよい。

### 4. GREEN の承認をユーザから得る
- ユーザに以下を提示する:
  - **テスト結果**: 該当テストが PASS していること(`colcon test` のサマリ)。
  - **既存テストへの影響**: 他のテストが壊れていないこと。
  - **実装差分**の要点。
- 承認が取れたら次のステップ(PR 作成)に進む。

### 5. PR を作成する
- 下記「手順」セクション(ステップ 5 以降)に従う。
- PR 本文に **RED ログ**と **GREEN ログ**の両方を貼る(承認の証跡として残す)。

## ブランチ命名
| 種類 | 命名規則 | 例 |
|---|---|---|
| 実装計画の Step | `step-<番号>-<短い識別子>` | `step-3-wrapper-node` |
| ドキュメントのみ | `docs/<短い識別子>` | `docs/development-workflow` |
| バグ修正 | `fix/<短い識別子>` | `fix/launch-config-path` |
| その他 | `chore/<短い識別子>` | `chore/update-gitignore` |

## 手順

### 1. ブランチを切る
```bash
git checkout main
git pull
git checkout -b step-<番号>-<識別子>
```

### 2. 作業する
- 該当 Step の DoD(Definition of Done)を満たすまで実装する。
- **ROS 2 ノードの機能を含む変更は、上記「TDD フロー」に従う**(RED → ユーザ承認 → GREEN → ユーザ承認)。テスト可能な機能でテストを省略しない。
- 上流挙動を維持する方針(`CLAUDE.md` の「規約」参照)を守る。
- コミットメッセージは日本語可。1 PR 内に複数コミットがあって構わないが、PR は Step 単位で分ける。

### 3. ローカルで動作確認
- ビルドが通ること: `colcon build --packages-select bbs3d_ros2`
- Step の DoD に動作確認が含まれる場合は、それも実施し PR 本文に結果を貼る。

### 4. 実装計画の checkbox を更新する(同 PR 内)
進捗とコードの整合を保つため、対応する Step の checkbox 更新は **同じ PR 内**で行う(別 PR に分けない)。

### 5. push して PR を作成
```bash
git push -u origin <branch-name>
gh pr create --title "<タイトル>" --body "$(cat <<'EOF'
## 対応する Step
IMPLEMENTATION_PLAN.md の Step <番号> — <題名>

## 変更概要
- <箇条書き>

## DoD チェック
- [ ] <DoD 項目 1>
- [ ] <DoD 項目 2>

## 動作確認
<コマンドと結果のサマリ>
EOF
)"
```

PR タイトルは 70 文字以内、英語/日本語どちらでも可。`feat:`/`fix:`/`docs:`/`chore:` のプレフィックスを推奨。

### 6. レビュー
- レビュー補助として `/review` や `/ultrareview` を使ってよい。
- ただし **最終承認はメンテナ(ユーザー)**。Claude のレビューだけでは main にマージしない。
- 指摘があれば同ブランチに追加コミットして対応する(force push は原則しない)。

### 7. マージ
```bash
gh pr merge --squash --delete-branch
```
- マージ方法は **squash** をデフォルトとする(履歴を Step 単位で読みやすくするため)。
- マージ後、ローカルの main を pull して同期する。

## テスト実行

### `BBS3D_REQUIRE_TEST_DATA` で skip / fail を切替
スモークテスト(`test/test_bbs3d_node_smoke.py`)はデフォルトで test data 未配置時に **skip** します(ローカル開発を妨げないため)。CI などで「データ未配置をサイレントに通したくない」場面では、環境変数 `BBS3D_REQUIRE_TEST_DATA=1` をセットすると **fail** に切り替わります(`true`、`yes` も同義、大小文字不問)。

```bash
# ローカル開発(デフォルト): data 無しなら skip
colcon test --packages-select bbs3d_ros2

# CI / 厳格モード: data 無しなら fail
BBS3D_REQUIRE_TEST_DATA=1 colcon test --packages-select bbs3d_ros2
```

CI を組む場合はこの env var を立てることを推奨。

## 例外
- **緊急修正**: ビルドが完全に壊れている等、main を即座に直す必要がある場合でも PR は通すが、レビューを最小限に縮め `--squash` で素早くマージしてよい。直接 push は依然として行わない。
- **submodule の更新**: `3d_bbs/` のコミットを更新する PR は、上流の変更内容と `sudo make install` の再実行が必要である旨を本文に明記する。

## 補足
- `IMPLEMENTATION_PLAN.md` は作業台帳であり、進捗 checkbox の更新は必ず PR 経由(本ドキュメントの手順 4)で行う。
- Claude セッション間で作業を引き継ぐ際は、`IMPLEMENTATION_PLAN.md` の最初の未完了 Step から再開する。
